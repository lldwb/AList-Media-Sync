# 运维部署

> 本文档覆盖 AList-Media-Sync 的三种部署方式、Docker 部署完整流程、数据持久化策略及运维注意事项。
> 环境变量完整清单详见 [环境变量清单.md](operations/环境变量清单.md)（单一权威来源，本文档不重复全量表）。

## 一、部署方式对比

| 维度 | Docker（推荐生产） | 一体化启动包（离线） | 源码构建（开发） |
|---|---|---|---|
| **适用场景** | 生产环境、CI/CD 流水线 | 离线环境、无 Docker 环境 | 本地开发、调试、贡献代码 |
| **前置条件** | Docker 24+、Docker Compose v2 | JRE 21+（目标机器） | JDK 21+、Node.js 22+、Maven |
| **启动命令** | `docker compose up -d` | `java -jar app.jar` | `./mvnw spring-boot:run` |
| **数据持久化** | Docker 命名卷 + 绑定挂载 | 文件系统目录（`./data`、`./logs`） | 文件系统目录（`./data`、`./logs`） |
| **前端构建** | Dockerfile 三阶段自动构建 | 预构建打包 | `npm run build` 或 DevServer |
| **FFmpeg 依赖** | 镜像内置 JAVE2 原生二进制 | 打包内置 JAVE2 原生二进制 | 需手动确认平台匹配 |
| **健康检查** | Docker Compose healthcheck | 手动 curl | 手动 curl |
| **升级方式** | 重新构建镜像 + `docker compose up -d` | 替换 JAR 文件 | `git pull` + 重新启动 |

## 二、Docker 部署完整流程

### 2.1 前置条件

- Docker 24.0+
- Docker Compose v2（`docker compose` 命令）
- 网络可访问 AList 服务器

### 2.2 配置 .env 文件

```bash
# 复制环境变量模板
cp .env.example .env

# 编辑 .env 文件
vi .env
```

最小化生产配置示例：

```bash
# .env 文件

# HTTP 服务端口（主机侧）
PORT=8080

# 日志级别（生产环境推荐 WARN）
LOGGING_LEVEL=WARN

# AList 服务器（必填）
ALIST_BASE_URL=https://alist.example.com
ALIST_TOKEN=your-actual-token

# AES-256 加密密钥（生产必设，生成方法：openssl rand -base64 32）
ALIST_CRYPTO_KEY="your-generated-base64-key"

# JVM 内存（根据转码并发调整）
JAVA_OPTS="-Xms256m -Xmx512m"
```

> 完整环境变量说明详见 [环境变量清单.md](operations/环境变量清单.md)。

### 2.3 构建与启动

```bash
# 构建镜像并启动（首次构建约 3-5 分钟）
docker compose up -d

# 查看容器状态
docker compose ps

# 查看启动日志
docker compose logs -f alist-media-sync
```

启动成功标志：日志输出 Spring Boot 启动横幅后出现 `Started AListMediaSyncApplication in X.XXX seconds`。

### 2.4 健康检查

```bash
# 方式一：curl 手动检查
curl http://localhost:8080/actuator/health
# 预期响应：{"status":"UP","components":{...}}

# 方式二：Docker Compose 自动健康检查
# docker-compose.yml 配置了 healthcheck，每 30 秒检查一次
# 容器启动 30 秒后开始检查，连续失败 3 次判定为不健康
docker compose ps
# STATUS 列显示 "healthy" 或 "unhealthy"
```

### 2.5 卷挂载策略

`docker-compose.yml` 配置了三个卷挂载：

| 挂载类型 | 容器路径 | 宿主机路径 | 用途 |
|---|---|---|---|
| 命名卷 | `/app/data` | Docker 管理（`alist-media-sync-data`） | H2 数据库文件持久化 |
| 绑定挂载 | `/app/logs` | `./logs` | 日志文件，宿主机可直接读取 |
| 绑定挂载 | `/app/diagnostics` | `./diagnostics` | 诊断包输出，宿主机可直接读取 |

**命名卷 vs 绑定挂载**：

- 数据目录使用命名卷，由 Docker 管理权限和生命周期，容器删除后卷保留
- 日志和诊断目录使用绑定挂载，运维人员可在宿主机直接查看，无需进入容器

**多实例限制**：本应用使用 H2 内嵌数据库（文件模式），数据库文件通过排他锁保护。同一数据卷只能同时运行一个容器实例。如需多实例部署，需使用独立的数据卷或外部数据库。

### 2.6 日志查看

```bash
# 实时查看容器日志（所有级别）
docker compose logs -f alist-media-sync

# 查看最近 100 行
docker compose logs --tail 100 alist-media-sync

# 查看应用日志文件（宿主机直接读取）
tail -f ./logs/app.log

# 查看错误日志文件
tail -f ./logs/error.log

# 按 traceId 过滤
grep "traceId=a1b2c3d4" ./logs/app.log
```

> 日志体系详解详见 [故障排查与日志.md](operations/故障排查与日志.md)。

### 2.7 停止与重启

```bash
# 停止（优雅关闭，12 秒内完成）
docker compose down

# 重启
docker compose restart

# 重新构建并启动（代码更新后）
docker compose build --no-cache && docker compose up -d
```

**优雅关闭机制**：

- `application.yaml` 配置 `spring.lifecycle.timeout-per-shutdown-phase: 12s`，收到 SIGTERM 后等待进行中的请求完成
- `docker-compose.yml` 配置 `stop_grace_period: 35s`，略大于应用优雅关闭超时，确保请求处理完毕
- Docker Compose 发送 SIGTERM 后等待 35 秒，应用在 12 秒内完成关闭，剩余时间作为缓冲

## 三、环境变量配置

环境变量完整清单详见 [环境变量清单.md](operations/环境变量清单.md)，该文档为单一权威来源（SSOT）。

本文档仅列出部署时必须配置的核心变量：

| 环境变量 | 必填 | 说明 |
|---|---|---|
| `ALIST_BASE_URL` | 是 | AList 服务器地址 |
| `ALIST_TOKEN` | 是 | AList API 认证令牌 |
| `ALIST_CRYPTO_KEY` | 生产必设 | AES-256 加密密钥，缺失则每次重启随机生成 |
| `APP_AUTH_PASSWORD` | 生产必填 | 管理后台密码，避免默认值 `admin123` |
| `LOGGING_LEVEL` | 否 | 生产环境推荐 `WARN` |
| `JAVA_OPTS` | 否 | JVM 内存参数，根据转码并发调整 |

## 四、数据持久化

### 4.1 H2 数据库文件

H2 文件模式数据库存储在 `${DATA_DIR}/alist_media_sync.*` 文件组中：

| 文件 | 用途 |
|---|---|
| `alist_media_sync.mv.db` | 主数据文件（表数据、索引） |
| `alist_media_sync.trace.db` | 跟踪日志（H2 内部） |
| `alist_media_sync.lock.db` | 排他锁文件（运行时存在） |

**Docker 环境**：位于命名卷 `/app/data/`，通过 `docker volume inspect alist-media-sync-data` 查看实际路径。

**本地环境**：位于 `./data/` 目录。

### 4.2 dataDir 迁移

如需迁移数据目录（如更换磁盘或扩容）：

**Docker 环境**：

```bash
# 1. 停止应用
docker compose down

# 2. 备份原数据卷（参见下文"备份与恢复"）

# 3. 修改 docker-compose.yml 卷挂载，或修改 .env 中 DATA_DIR
#    注意：Docker 环境中 DATA_DIR 由 docker-compose.yml 固定为 /app/data
#    迁移需修改 docker-compose.yml volumes 配置

# 4. 恢复数据到新位置

# 5. 启动
docker compose up -d
```

**本地环境**：

```bash
# 1. 停止应用

# 2. 迁移数据目录
mv ./data /new/path/data

# 3. 修改环境变量
export DATA_DIR=/new/path/data

# 4. 启动应用
```

### 4.3 日志轮转

日志文件由 Logback 自动轮转，无需额外配置：

| 文件 | 滚动策略 | 单文件上限 | 保留天数 | 总大小上限 |
|---|---|---|---|---|
| `app.log` | 按天 + 按大小 | 50MB | 30 天 | 5GB |
| `error.log` | 按天 + 按大小 | 50MB | 30 天 | 2GB |

滚动文件自动 gzip 压缩，命名格式：`app.2026-07-02.0.log.gz`。

Docker 环境中日志通过绑定挂载输出到宿主机 `./logs/`，宿主机可直接清理历史日志：

```bash
# 清理 7 天前的滚动日志
find ./logs -name "*.log.gz" -mtime +7 -delete
```

### 4.4 备份与恢复

**Docker 环境（命名卷备份）**：

```bash
# 备份
docker run --rm \
    -v alist-media-sync-data:/data \
    -v $(pwd):/backup \
    alpine tar czf /backup/alist-data-backup-$(date +%Y%m%d).tar.gz -C /data .

# 恢复
docker run --rm \
    -v alist-media-sync-data:/data \
    -v $(pwd):/backup \
    alpine tar xzf /backup/alist-data-backup-20260702.tar.gz -C /data
```

**本地环境（文件复制）**：

```bash
# 备份（应用停止状态下执行）
tar czf data-backup-$(date +%Y%m%d).tar.gz -C ./data .

# 恢复
tar xzf data-backup-20260702.tar.gz -C ./data
```

> 注意：备份前必须停止应用，避免 H2 数据库文件在写入时被复制导致损坏。

## 五、运维注意事项

### 5.1 FFmpeg/JAVE2 依赖

AList-Media-Sync 使用 JAVE2（Java Audio Video Encoder）作为转码引擎，内置 win64 和 linux64 原生 FFmpeg 二进制。

**平台限制**：

| 平台 | 支持情况 | 说明 |
|---|---|---|
| linux64 (x86_64) | 支持 | Docker 镜像基于 `eclipse-temurin:21-jre-alpine`（x86_64） |
| win64 (x86_64) | 支持 | 本地开发环境 |
| linux64 (ARM) | 不支持 | 内置二进制不兼容，需自行挂载系统 FFmpeg |
| macOS | 不支持 | 需自行挂载系统 FFmpeg（如通过 Homebrew 安装） |

**Docker 镜像 FFmpeg 来源**：

JAVE2 在运行时从 JAR 包内提取原生 FFmpeg 二进制到临时目录执行，Docker 镜像无需额外安装 FFmpeg。若遇到权限问题，确认 `appuser`（UID 1000）对 `TRANSCODE_TEMP_DIR` 有读写权限。

### 5.2 转码并发与内存关系

`TRANSCODE_MAX_CONCURRENT`（默认 32）控制最大并发转码任务数。每个转码任务启动独立 FFmpeg 子进程，消耗堆外内存（off-heap memory），与 `JAVA_OPTS` 的堆内存上限联动。

**推荐配置**：

| 转码并发 | JAVA_OPTS 堆内存 | 容器内存限制 | 适用场景 |
|---|---|---|---|
| 8 | `-Xms128m -Xmx256m` | 512MB | 轻量场景、低并发 |
| 16 | `-Xms256m -Xmx512m` | 1GB | 中等负载 |
| 32（默认） | `-Xms256m -Xmx512m` | 2GB | 高并发，需监控 OOM |
| 32+ | 不推荐 | — | 建议拆分多实例或使用外部转码服务 |

**配置方法**：

```bash
# .env 文件
TRANSCODE_MAX_CONCURRENT=16
JAVA_OPTS="-Xms256m -Xmx512m"

# 或 Docker Compose 启动时指定
TRANSCODE_MAX_CONCURRENT=16 JAVA_OPTS="-Xms256m -Xmx512m" docker compose up -d
```

> 注意：Docker 容器内 `Runtime.availableProcessors()` 可能返回宿主机核心数，因此 `TRANSCODE_MAX_CONCURRENT` 使用静态默认值 32 作为保守上限，不自动根据 CPU 核心数调整。

### 5.3 虚拟线程监控

应用启用 Java 21 虚拟线程（`spring.threads.virtual.enabled: true`），所有 HTTP 请求和异步任务在虚拟线程上执行。

**监控方法**：

```bash
# 查看线程数（虚拟线程不直接显示在 top 中）
docker compose exec alist-media-sync jcmd $(pgrep -f app.jar) Thread.print | grep "virtual"

# 通过 Actuator 查看线程状态
curl http://localhost:8080/actuator/health | jq .components
```

**注意事项**：

- 虚拟线程适用于 IO 密集型任务（HTTP 请求、AList API 调用）
- 转码任务通过独立线程池（`app.pool.*`）管理，不使用虚拟线程
- 若出现虚拟线程泄漏，检查 `synchronized` 块或 native 方法调用是否阻塞虚拟线程

### 5.4 Actuator 端点

`application.yaml` 仅暴露 `health` 端点：

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health
  endpoint:
    health:
      show-details: always
```

可用端点：

| 端点 | 路径 | 说明 |
|---|---|---|
| health | `GET /actuator/health` | 健康检查，显示 UP/DOWN 状态及各组件详情 |

> `show-details: always` 会暴露数据库、磁盘等组件的健康详情。生产环境如需隐藏详情，改为 `show-details: when_authorized`。

### 5.5 诊断包生成

详见 [故障排查与日志.md - 诊断包生成](operations/故障排查与日志.md#诊断包生成)。

快速生成：

```bash
# Docker 环境
docker compose exec alist-media-sync sh /app/scripts/diagnose.sh

# 输出位置：./diagnostics/latest/
```

### 5.6 升级、回滚与备份

#### 升级流程

```bash
# 1. 备份当前数据（重要！）
docker run --rm \
    -v alist-media-sync-data:/data \
    -v $(pwd):/backup \
    alpine tar czf /backup/alist-data-backup-pre-upgrade-$(date +%Y%m%d).tar.gz -C /data .

# 2. 拉取最新代码
git pull origin main

# 3. 重新构建并启动
docker compose build --no-cache && docker compose up -d

# 4. 验证健康状态
curl http://localhost:8080/actuator/health

# 5. 查看启动日志确认无异常
docker compose logs --tail 50 alist-media-sync
```

#### 回滚流程

```bash
# 1. 停止当前版本
docker compose down

# 2. 回退代码到上一个稳定版本
git log --oneline -10  # 找到稳定版本 commit
git checkout <stable-commit-hash>

# 3. 恢复数据（如有数据回退需求）
docker run --rm \
    -v alist-media-sync-data:/data \
    -v $(pwd):/backup \
    alpine tar xzf /backup/alist-data-backup-pre-upgrade-20260702.tar.gz -C /data

# 4. 重新构建并启动
docker compose build --no-cache && docker compose up -d
```

> 注意：H2 数据库使用 `ddl-auto: update`（`application.yaml` 第 29 行），升级时自动更新表结构。回滚到旧版本时，新增的表结构字段可能不被旧代码识别，通常不影响运行（JPA 忽略未映射的列）。生产环境建议将 `ddl-auto` 改为 `validate` 并使用 Flyway/Liquibase 管理迁移。

#### 备份策略建议

| 备份类型 | 频率 | 保留时长 | 方法 |
|---|---|---|---|
| 数据卷备份 | 每日 | 7 天 | `docker run --rm` + `tar czf` |
| 升级前备份 | 每次升级前 | 30 天 | 同上 |
| 日志归档 | 自动 | 30 天 | Logback 自动滚动 + gzip |

## 六、测试 Profile 与 CI 集成

### 6.1 测试分层与 Maven Profile

项目测试分为三层，通过 Maven profile 隔离执行，避免慢速测试污染常规开发反馈（FR-005）。

| Profile | 命令 | 执行范围 | 外部依赖 |
|---------|------|---------|---------|
| 默认 | `./mvnw test` | 单元测试（`*Test.java`） | 无 |
| integration | `./mvnw verify -Pintegration` | 单元 + 集成测试（`*IT.java`） | 无（H2 内存 + WireMock） |
| e2e | `./mvnw verify -Pe2e` | 单元 + 集成 + 端到端测试（`*E2ETest.java`） | AList 二进制（录播姬可选） |

集成测试覆盖 6 个 Repository（`@DataJpaTest`）与 AList 客户端契约（WireMock），验证数据完整性约束与外部契约交互。端到端测试通过 webhook payload 重放驱动真实系统与真实 AList 链路，验证 3 条核心业务链路 + traceId 全链路传播。

E2E 测试采用串行执行（failsafe `forkCount=1`，FR-012）与套件级超时兜底（`forkedProcessExitTimeoutInSeconds=900`，SC-006），单链路 `@Timeout(15, MINUTES)`。

### 6.2 nightly CI 定时运行

E2E 测试套件总时长约 60 分钟（SC-006），不适宜阻塞 PR 协作流水线，仅以定时任务方式运行（FR-013）：

- **PR 流水线**：仅运行 `./mvnw verify -Pintegration`（单元 + 集成测试，无外部依赖）
- **nightly 定时**：GitHub Actions `schedule.cron` 触发 `./mvnw verify -Pe2e`，CI 脚本调用 `scripts/e2e/prepare-e2e-env.sh` 下载 AList 二进制
- **失败处理**：nightly 失败通过 CI 通知机制告警，不阻塞 PR 合并

nightly 工作流配置文件位于 `.github/workflows/e2e-nightly.yml`。E2E 环境搭建详见 [02-开发环境搭建.md §7](./02-开发环境搭建.md#7-端到端测试环境搭建)。
