# 交叉关注点

> 本文档为 US4 架构设计细化文档之一，描述跨模块的横切关注点。总览见 [03-架构设计.md](../03-架构设计.md)。

## 认证

### 机制

项目采用 HTTP Basic 认证，不引入完整 Spring Security 框架（遵循章程原则 VI — YAGNI），仅使用 Spring Security Crypto 的 BCrypt 密码哈希。

### 核心组件

| 组件 | 职责 |
|---|------|
| `AuthInterceptor` | HTTP Basic 认证拦截器（约 80 行），排除 `/api/webhooks/**`、`/actuator/health` |
| `WebSocketAuthInterceptor` | WebSocket 握手阶段 Basic Auth 校验 |
| `PasswordEncryptionPostProcessor` | `EnvironmentPostProcessor`，启动时将明文密码 BCrypt 加密到内存，绝不回写配置文件 |
| `AppProperties.auth` | 认证配置（username / password），password 在内存中已被 BCrypt 加密 |

### 认证流程

1. 用户配置明文密码（`app.auth.password` 或环境变量 `APP_AUTH_PASSWORD`）
2. 启动时 `PasswordEncryptionPostProcessor` 将明文密码 BCrypt 加密后替换内存中的值
3. 请求到达时，`AuthInterceptor` 从 `Authorization` 头解析 Basic 凭据
4. 用户名直接比对，密码通过 BCrypt 比对
5. 认证失败返回 401

### 安全边界

- **受保护路径**：所有 `/api/**` 路径（除 webhook 和 health）
- **公开路径**：`/api/webhooks/**`（录播姬推送事件）、`/actuator/health`（健康检查）
- **WebSocket**：`/ws/events` 端点在握手阶段认证

## 加密

### 机制

Token 等敏感字段使用 AES-256-GCM 加密存储在数据库中，加密/解密由 JPA `AttributeConverter` 自动完成。

### 核心组件

| 组件 | 职责 |
|---|------|
| `CryptoConverter` | JPA `AttributeConverter<String, String>`，AES-256-GCM 加密/解密数据库字段 |
| `CryptoKeyEnvironmentPostProcessor` | `EnvironmentPostProcessor`，将 `ALIST_CRYPTO_KEY` 环境变量桥接到 JVM 系统属性 |
| `StorageEngine.encryptedToken` | 使用 `@Convert(converter = CryptoConverter.class)` 的 Token 字段 |

### 加密流程

1. `ALIST_CRYPTO_KEY` 环境变量配置 Base64 编码的 32 字节密钥（可选）
2. 启动时 `CryptoKeyEnvironmentPostProcessor` 将环境变量桥接到 `System.getProperty("alist.crypto.key")`
3. 未配置时随机生成密钥（重启后已加密数据不可解密，仅适用于开发环境）
4. 写入数据库时，`CryptoConverter.convertToDatabaseColumn()` 自动加密
5. 读取数据库时，`CryptoConverter.convertToEntityAttribute()` 自动解密
6. 业务代码无感知，始终操作明文

## 虚拟线程

### 机制

项目基于 Java 21，启用虚拟线程支持，提升 I/O 密集型场景的并发能力。

### 配置

```yaml
spring:
  threads:
    virtual:
      enabled: true
```

### 影响范围

- Spring Boot 自动将 Tomcat 请求处理线程切换为虚拟线程
- `@Async` 任务可运行在虚拟线程上（取决于线程池配置）
- 转码线程池（`AsyncConfig.transcodeExecutor`）仍使用平台线程池（核 8 / 最大 32），因为 FFmpeg 转码是 CPU 密集型操作，虚拟线程无优势
- 虚拟线程适用于文件下载、上传等 I/O 等待场景

## 诊断

### 三种入口

遵循章程原则 VII §7.10，系统提供三种诊断生成入口：

| 入口 | 路径 | 适用场景 |
|---|---|---|
| 脚本 | `diagnose.sh` / `diagnose.bat` | 本地开发、一体化启动包 |
| API | `POST /api/diagnostics/run` | Docker 部署、远程触发（受认证保护） |
| Web | 管理前端诊断按钮 | 复用 API 入口 |

### 核心组件

| 组件 | 职责 |
|---|------|
| `DiagnosticService` | 诊断系统核心，收集日志摘要、配置信息（脱敏）、系统信息、数据库状态（位于 `ops/`） |
| `DiagnosticController` | 诊断 API 端点（位于 `ops/`） |
| `DiagnosticResultVO` | 诊断结果 VO（位于 `common/dto/`） |

### 诊断包内容

- 日志摘要（最近 N 条 ERROR 日志）
- 配置信息（敏感字段脱敏）
- 系统信息（JVM 版本、内存、磁盘空间）
- 数据库状态（引擎连接状态、任务执行统计）
- 输出到 `diagnostics/{timestamp}/` 目录，含 `summary.md` 摘要文件

### 约束

- 30 秒内输出诊断包路径与摘要文件位置
- 诊断生成过程为只读操作，不触发同步、转码、Webhook 等业务副作用

## 日志

### 规范来源

日志规范定义于 `.specify/memory/constitution.md` §VII（原则 VII），此处为架构层面的关联说明。

### 核心组件

| 组件 | 职责 |
|---|------|
| `TraceIdFilter` | `OncePerRequestFilter`，请求入口生成/继承 traceId，写入 MDC，设置 `X-Trace-Id` 响应头 |
| `TraceContext` | MDC 上下文管理，提供 `runWith(traceId, module, operation, runnable)` 便捷入口和 `clear()` 清理 |
| `SensitiveDataMasker` | 敏感数据脱敏工具，替换密码/Token/密钥为 `***` |

### 结构化 MDC 字段

每条业务日志的 MDC 至少包含：

- `traceId`：唯一链路标识（长度 8-128，仅含字母数字、`-`、`_`、`.`）
- `module`：模块标识（sync / transcode / webhook / storage）
- `operation`：操作标识（如"同步任务执行"、"转码任务创建"）
- `errorType`：ERROR 级别日志额外写入异常类别简短标识

### 日志双写

- `app.log`：全级别日志（DEBUG / INFO / WARN / ERROR）
- `error.log`：仅 ERROR 级别日志，由 Logback Appender 强制分流
- 同一条 ERROR 日志同时出现在两个文件中
- 滚动策略按日切分，保留最近 7 天

### X-Trace-Id 响应头

- 所有 `/api/**` HTTP 响应通过 `TraceIdFilter` 统一注入 `X-Trace-Id` 响应头
- 值为当前 MDC 中的 traceId
- 异常路径（4xx / 5xx）下同样存在

### 敏感数据脱敏

- 日志消息和诊断包内容不出现原始密码、Token、API Key、加密密钥、`Authorization` 头、`Cookie` 头
- 调用外部 API 时，请求/响应日志对认证头和请求体中的敏感字段做脱敏
- 配置摘要日志标注敏感字段为"已配置/未配置"，不打印实际值
- 疑似凭据含义的配置键（含 password / token / secret / key / auth / cookie 关键字）默认按敏感处理
