# 故障排查与日志

> 本文档覆盖 AList-Media-Sync 的日志体系、traceId 串联查询机制、错误日志分流策略，以及常见问题的排查方法。
> 环境变量配置详见 [环境变量清单.md](环境变量清单.md)。

## 一、日志体系概述

AList-Media-Sync 使用 Logback（Spring Boot 默认）管理日志，配置文件位于 `src/main/resources/logback-spring.xml`。

### 日志文件

| 文件 | 路径 | 内容 | 滚动策略 |
|---|---|---|---|
| `app.log` | `${LOG_PATH}/app.log` | 所有级别日志（TRACE → ERROR） | 按天滚动，单文件最大 50MB，保留 30 天，总上限 5GB |
| `error.log` | `${LOG_PATH}/error.log` | 仅 ERROR 级日志 | 按天滚动，单文件最大 50MB，保留 30 天，总上限 2GB |

> Docker 环境中 `LOG_PATH` 由 `docker-compose.yml` 固定为 `/app/logs`，并通过绑定挂载映射到宿主机 `./logs/` 目录。

### 日志输出格式

控制台与文件采用相同的 Pattern（定义于 `application.yaml` 第 65-66 行）：

```
%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] [traceId=%X{traceId:-}] [module=%X{module:-}] [operation=%X{operation:-}] [errorType=%X{errorType:-}] %logger{36} - %msg%n
```

示例输出：

```
2026-07-02 14:23:45.123 INFO  [http-nio-8080-exec-1] [traceId=a1b2c3d4] [module=sync] [operation=syncFolder] [] c.t.a.common.controller.SyncController - 同步任务已启动
2026-07-02 14:23:46.456 ERROR [http-nio-8080-exec-1] [traceId=a1b2c3d4] [module=sync] [operation=syncFolder] [errorType=NetworkError] c.t.a.common.service.SyncService - AList API 调用失败: 连接超时
```

## 二、日志级别调整

### 全局日志级别

通过环境变量 `LOGGING_LEVEL` 控制全局日志级别，取值如下：

| 取值 | 说明 | 适用场景 |
|---|---|---|
| `TRACE` | 最详细，包含所有方法入参出参 | 深度调试 |
| `DEBUG` | 调试信息，包括 SQL 参数、请求体 | 开发调试 |
| `INFO` | 关键业务流程日志（默认） | 日常运行 |
| `WARN` | 仅警告及以上 | 生产环境推荐 |
| `ERROR` | 仅错误 | 问题定位 |
| `OFF` | 关闭所有日志 | 不推荐 |

配置方式：

```bash
# .env 文件
LOGGING_LEVEL=WARN

# docker compose 启动时临时指定
LOGGING_LEVEL=DEBUG docker compose up -d
```

### 业务包单独控制

业务包 `top.lldwb.alistmediasync` 的日志级别在 `application.yaml` 第 53 行单独配置，默认跟随 `LOGGING_LEVEL`：

```yaml
logging:
  level:
    root: ${LOGGING_LEVEL:INFO}
    top.lldwb.alistmediasync: ${LOGGING_LEVEL:INFO}
```

如需在生产环境保持全局 `WARN` 但业务包 `INFO`，可修改 `application.yaml` 中业务包级别为固定值：

```yaml
top.lldwb.alistmediasync: INFO
```

> 注意：`logback-spring.xml` 第 65 行硬编码了业务包级别为 `INFO`（`<logger name="top.lldwb.alistmediasync" level="INFO" additivity="true"/>`）。若需通过环境变量动态控制业务包级别，需同步修改此行。

### 静默噪音日志

以下日志级别已在 `application.yaml` 中预设为 `WARN`，避免噪音：

- `org.springframework.web.servlet.resource: WARN` — 静态资源 404（浏览器缓存旧版构建、DevTools 探测请求触发）不输出错误堆栈

## 三、traceId 串联查询

### MDC 字段

每个 HTTP 请求进入时，`TraceIdFilter`（`src/main/java/top/lldwb/alistmediasync/common/config/TraceIdFilter.java`）自动注入以下 MDC 字段：

| MDC 字段 | 含义 | 填充时机 |
|---|---|---|
| `traceId` | 请求级唯一追踪 ID | `TraceIdFilter` 从 `X-Trace-Id` 请求头读取，若合法则沿用，否则生成新值 |
| `module` | 业务模块标识（如 `sync`、`transcode`、`webhook`） | Service/Controller 层按业务设置 |
| `operation` | 具体操作名（如 `syncFolder`、`transcodeFile`） | Service 层方法级设置 |
| `errorType` | 错误类型分类（如 `NetworkError`、`AuthError`） | 异常处理器 `GlobalExceptionHandler` 设置 |

### X-Trace-Id 响应头

所有 `/api/**` 路径的 HTTP 响应（包括成功、业务失败、认证失败、异常路径）均携带 `X-Trace-Id` 响应头。实现位于 `TraceIdFilter`：

```java
// 提前写入响应头，确保异常路径也能被客户端读到
response.setHeader(HEADER_TRACE_ID, traceId);
```

客户端可通过响应头获取 `traceId`，再到日志中按该值过滤查询。

### 日志串联查询方法

**场景**：用户报告"14:23 左右同步失败"，响应头返回 `X-Trace-Id: a1b2c3d4`。

```bash
# 1. 按 traceId 过滤应用日志
grep "traceId=a1b2c3d4" ./logs/app.log

# 2. 按 traceId 过滤错误日志
grep "traceId=a1b2c3d4" ./logs/error.log

# 3. 查看该请求的所有日志（从入口到异常）
grep "traceId=a1b2c3d4" ./logs/app.log | less

# 4. Docker 环境
docker compose exec alist-media-sync grep "traceId=a1b2c3d4" /app/logs/app.log
```

**场景**：无 traceId，按时间范围查询。

```bash
# 查找 14:20-14:25 之间的所有 ERROR 日志
grep "2026-07-02 14:2[0-5]" ./logs/error.log | grep "ERROR"
```

## 四、error.log 分流

### 分流机制

Logback 配置（`logback-spring.xml`）使用 `ThresholdFilter` 将 ERROR 级日志同时写入两个文件：

- **`app.log`**：所有级别日志（含 ERROR），通过 `APP_FILE` appender 输出
- **`error.log`**：仅 ERROR 级，通过 `ERROR_FILE` appender 输出（`<level>ERROR</level>` 过滤）

两个 appender 均挂载到 root logger（第 68-72 行），因此每条 ERROR 日志同时写入两个文件。

### 滚动策略

| 文件 | 滚动策略 | 单文件上限 | 保留天数 | 总大小上限 |
|---|---|---|---|---|
| `app.log` | `SizeAndTimeBasedRollingPolicy`（按天 + 按大小） | 50MB | 30 天 | 5GB |
| `error.log` | `SizeAndTimeBasedRollingPolicy`（按天 + 按大小） | 50MB | 30 天 | 2GB |

滚动文件命名格式：`app.2026-07-02.0.log.gz`（日期 + 序号 + gzip 压缩）。

## 五、常见问题 FAQ

### 5.1 启动失败

#### 端口被占用

**现象**：启动日志出现 `Port 8080 was already in use` 或 `BindException: Address already in use`。

**排查**：

```bash
# 查看占用 8080 端口的进程
# Linux/Docker
lsof -i :8080
# Windows
netstat -ano | findstr :8080

# 解决方案：释放端口或更换端口
# .env 文件
PORT=8081
SERVER_PORT=8081
```

#### H2 数据库文件锁定

**现象**：启动日志出现 `Database may be already in use` 或 `The database is already in use`。

**排查**：

H2 文件模式通过排他锁保护，同一数据库文件只能同时被一个进程打开。常见原因：

1. 之前的实例未正常关闭，锁文件未释放
2. 同一数据卷运行了多个容器实例（参见 `docker-compose.yml` 第 18-20 行注释）

```bash
# 检查是否有残留的 .lock.db 文件
ls -la ./data/*.lock.db

# 若确认无进程占用，删除锁文件
rm ./data/*.lock.db

# Docker 环境：检查是否有多实例
docker compose ps
docker ps | grep alist-media-sync
```

> 注意：切勿在应用运行时删除锁文件，会导致数据库损坏。仅在前一个进程已确认退出时操作。

### 5.2 转码失败

#### FFmpeg 原生二进制不可用

**现象**：转码日志出现 `Cannot run program "ffmpeg"` 或 `Native library not found`。

**排查**：

AList-Media-Sync 使用 JAVE2（基于包装的 FFmpeg）进行转码，内置 win64 和 linux64 原生 FFmpeg 二进制。

```bash
# 检查转码临时目录是否可写
docker compose exec alist-media-sync ls -la /tmp/alist-media-sync/transcode/

# 检查 FFmpeg 二进制是否被正确提取
docker compose exec alist-media-sync find / -name "ffmpeg" -type f 2>/dev/null

# 确认操作系统架构匹配
docker compose exec alist-media-sync uname -m
# 应输出 x86_64（linux64 二进制仅支持 x86_64 架构）
```

**解决**：

- ARM 架构（如树莓派、Apple Silicon）不支持内置的 linux64 FFmpeg 二进制，需自行挂载系统 FFmpeg
- 容器内权限问题：确认 `appuser`（UID 1000）对转码临时目录有读写权限

#### 内存不足导致 OOM

**现象**：转码任务大量并发时容器被 OOM Kill（`docker inspect` 显示 `OOMKilled: true`）。

**排查**：

`TRANSCODE_MAX_CONCURRENT`（默认 32）与 `JAVA_OPTS`（默认 `-Xmx256m`）需要联动调整。每个并发转码任务启动独立 FFmpeg 子进程，消耗堆外内存。

```bash
# 查看容器内存限制
docker inspect alist-media-sync | grep -A5 Memory

# 查看当前并发转码数
docker compose logs -f | grep "转码任务"

# 查看是否被 OOM Kill
docker inspect alist-media-sync | grep -i oomkill
```

**解决**：参见 [06-运维部署.md - 转码并发与内存关系](../06-运维部署.md#转码并发与内存关系)。

### 5.3 Webhook 不触发

#### 规则匹配失败

**现象**：AList 侧文件变更后，AList-Media-Sync 未执行同步。

**排查**：

```bash
# 1. 检查 Webhook 事件是否到达应用
grep "module=webhook" ./logs/app.log | tail -20

# 2. 检查规则匹配日志
grep "operation=matchRule" ./logs/app.log

# 3. 检查事件是否被去重
grep "operation=dedup" ./logs/app.log
```

常见原因：

- `SERVER_ADDRESS` 未正确配置，AList 无法回调到本应用
- Webhook 规则中的路径模式与实际文件路径不匹配
- 事件去重窗口期内收到重复事件被丢弃

#### 事件去重导致跳过

**现象**：短时间内多次文件变更只触发一次同步。

这是预期行为。AList-Media-Sync 对同一路径的事件在去重窗口期内合并处理，避免重复同步。如需调整去重策略，检查相关配置。

### 5.4 AList API 调用失败

#### Token 无效或过期

**现象**：日志出现 `module=alist` 和 `errorType=AuthError`，AList API 返回 401。

**排查**：

```bash
# 按错误类型过滤日志
grep "errorType=AuthError" ./logs/error.log

# 检查 ALIST_TOKEN 是否正确
# 注意：不要在日志中打印 token 值，使用以下命令检查是否设置
docker compose exec alist-media-sync printenv ALIST_TOKEN | head -c 4
# 应输出 token 的前 4 个字符
```

**解决**：

- 从 AList 管理后台重新获取 Token，更新 `.env` 文件中的 `ALIST_TOKEN`
- 重启容器：`docker compose up -d`

#### 网络不可达

**现象**：日志出现 `module=alist` 和 `errorType=NetworkError`，连接超时或拒绝。

**排查**：

```bash
# 从容器内测试 AList 连通性
docker compose exec alist-media-sync wget --spider --timeout=5 ${ALIST_BASE_URL}

# 检查 DNS 解析
docker compose exec alist-media-sync nslookup alist.example.com
```

### 5.5 诊断包生成

AList-Media-Sync 提供两种诊断包生成方式：

#### 方式一：diagnose.sh 脚本

适用于容器无法启动或 API 不可用时。

```bash
# Docker 环境执行
docker compose exec alist-media-sync sh /app/scripts/diagnose.sh

# 自定义输出目录和 traceId
docker compose exec alist-media-sync sh /app/scripts/diagnose.sh \
    --output /app/diagnostics/manual-test \
    --trace-id manual-test-001 \
    --max-lines 500

# 本地开发环境
sh scripts/diagnose.sh --output ./diagnostics/latest
```

诊断包输出到 `./diagnostics/latest/`，包含：

| 文件 | 内容 |
|---|---|
| `summary.md` | 诊断摘要（时间、部署形态、缺失信息、建议） |
| `logs/error.log` | 错误日志末尾 N 行（默认 2000），敏感字段已脱敏 |
| `logs/app.log` | 应用日志末尾 N 行，敏感字段已脱敏 |
| `environment.txt` | 环境变量（敏感字段已脱敏）、系统信息（OS/CPU/内存/磁盘） |
| `config/config.redacted.json` | 配置文件列表（值已脱敏） |

退出码：`0` 成功，`2` 部分信息不可用但摘要已生成，`1` 生成失败。

#### 方式二：API 端点

适用于服务正常运行时获取更完整的诊断包。

```bash
# 触发诊断包生成
curl -X POST http://localhost:8080/api/diagnostics/run \
     -H "X-Trace-Id: manual-diag-001"

# 响应中包含诊断包路径或下载链接
```

> 诊断包中的敏感信息（Token、密码、密钥）均通过 `diagnose.sh` 的 `awk` 正则匹配脱敏，脱敏后显示为 `***REDACTED***`。参见 `scripts/diagnose.sh` 第 92-97 行和第 121-128 行。
