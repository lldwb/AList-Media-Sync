## 澄清

### 会话 2026-07-19

- Q: E2E 测试套件的并行执行策略？ -> A: 链路间串行执行（@Execution(SAME_THREAD) 或 failsafe forkCount=1），每条链路独立清理状态
- Q: E2E 全局超时阈值？ -> A: 单链路全局超时 15 分钟，超时即标记失败并清理状态（总套件上限约 60 分钟）
- Q: SC-004 中直播源不可用（skip）的判定？ -> A: skip 不计入"通过"，3 次必须全部真实执行且成功

### 会话 2026-07-23

- Q: 直播源不可用时端到端测试的降级策略？ -> A: 完全放弃真实录制直播流，改为 webhook payload 重放驱动 + 真实 AList 与系统实例，录播姬仅作为可选验证（不依赖真实直播源）
- Q: 端到端测试是否要求在 CI 环境中运行？ -> A: E2E 纳入 CI 但仅定时运行（如 nightly），PR 流水线不触发 E2E（CI 仅运行单元 + 集成测试层）
- Q: AList 与录播姬实例端口被占用时如何处理？ -> A: 动态端口分配（自动探测空闲端口并注入到 AList/录播姬/系统配置），消除端口冲突风险
- Q: 端到端测试中途失败时系统状态如何处理？ -> A: 失败后保留现场（数据库、文件系统）供诊断，下次运行前强制清理保证幂等（不立即清理失败现场）

### 用户故事 1 - 运行端到端测试验证完整业务链路（优先级：P1）

作为维护者，我希望在本地一键运行端到端测试，验证从录播姬 webhook 事件接收、文件同步到 AList、媒体转码的完整业务链路真实可用，以确保系统在真实外部依赖下的行为符合预期。

**为什么是此优先级**：当前测试金字塔仅有单元测试层（37 个测试文件），缺少集成与端到端层。单元测试用 Mock 隔离了外部依赖，无法发现"系统与真实 AList/录播姬 交互时的契约偏差、数据持久化丢失、链路中断"等问题。端到端测试是验证"系统作为整体在真实环境中能否工作"的唯一手段，是回归质量保障的最高优先级缺口。

**独立测试**：可以通过"启动本地 AList 与录播姬实例 -> 触发录播姬 webhook -> 观察系统同步与转码结果"完整测试并交付"全链路真实可用"的价值。

**验收场景**：

1. **假设** 本地已准备 AList 与录播姬实例，**当** 维护者触发端到端测试，**则** 测试自动启动系统、接收录播姬 webhook、将文件同步到 AList 并完成转码，全链路断言通过
2. **假设** 系统接收到录播姬"录制完成"webhook，**当** webhook 事件被处理，**则** 对应文件被同步到 AList 目标路径，且任务执行历史持久化到数据库
3. **假设** 同一 webhook 事件被重复发送，**当** 系统第二次接收，**则** 幂等去重命中，不产生重复同步任务（验证章程原则 II 数据完整性）
4. **假设** 端到端链路执行中，**当** 任意阶段发生，**则** 全链路日志携带同一 traceId，可通过诊断包追溯完整链路（验证章程原则 VII）

### 用户故事 2 - 补全集成测试覆盖 Repository 与外部 API 客户端（优先级：P2）

作为维护者，我希望补全 Repository 层与外部 API 客户端（AList）的集成测试，以验证数据持久化行为与外部契约交互的真实正确性，填补单元测试与端到端测试之间的中间层缺口。

**为什么是此优先级**：章程原则 V 明确要求"所有 Repository 方法和外部 API 客户端 MUST 有集成测试"，当前完全缺失。集成测试比端到端测试轻量、快速，能精确定位"数据层或契约层"的问题，是测试金字塔中性价比最高的中间层。

**独立测试**：可以通过"针对每个 Repository 运行真实数据库交互测试、针对 AList 客户端运行契约模拟测试"完整测试并交付"数据层与契约层正确性"的价值。

**验收场景**：

1. **假设** Repository 层有实体持久化方法，**当** 运行集成测试，**则** 验证乐观锁、事务回滚、级联关系等数据完整性行为真实生效（章程原则 II）
2. **假设** AList API 客户端调用外部接口，**当** 运行基于契约模拟的集成测试，**则** 验证请求构造、响应解析、错误处理、重试机制符合 AList 外部契约
3. **假设** 集成测试被纳入常规测试套件，**当** 维护者运行常规测试命令，**则** 集成测试随单元测试一起执行，无需额外配置

### 用户故事 3 - 一键准备端到端测试环境（优先级：P3）

作为维护者，我希望通过一个命令在项目目录下载并准备 AList 与录播姬的可执行实例，以降低端到端测试环境搭建的成本，确保任何新贡献者都能快速复现测试环境。

**为什么是此优先级**：端到端测试的前提是外部依赖可用。如果环境搭建依赖人工下载、配置，将严重阻碍测试的采用与维护。一键准备脚本是把"端到端测试能力"从"理论上可用"变为"实际可执行"的关键基础设施。

**独立测试**：可以通过"在干净项目目录执行准备脚本 -> 验证 AList 与录播姬可启动并响应"完整测试并交付"环境可复现"的价值。

**验收场景**：

1. **假设** 项目目录是干净状态（未下载外部依赖），**当** 维护者执行环境准备命令，**则** AList 与录播姬可执行文件被下载到项目指定目录，并完成基础配置
2. **假设** 外部依赖已下载，**当** 维护者再次执行准备命令，**则** 跳过已存在的下载，仅校验完整性（幂等）
3. **假设** 下载源不可达，**当** 准备命令执行失败，**则** 输出清晰的错误信息与备选方案（如手动下载指引）

## 需求 *（强制）*

### 功能需求

- **FR-001**：系统必须提供端到端测试套件，覆盖从录播姬 webhook 事件接收、系统处理、AList 文件同步到媒体转码的完整业务链路
- **FR-002**：系统必须在项目目录提供 AList 与录播姬可执行实例的下载与启动能力，用于端到端测试真实外部依赖
- **FR-003**：系统必须补全 Repository 层集成测试，验证实体持久化、乐观锁、事务行为等数据完整性约束（章程原则 II、V）
- **FR-004**：系统必须补全外部 API 客户端（AList）集成测试，验证请求构造、响应解析、错误处理与重试机制符合外部契约
- **FR-005**：端到端测试必须通过独立的测试 profile 触发，不污染常规单元测试与集成测试的执行
- **FR-006**：端到端测试必须验证 traceId 在全链路的传播与持久化，确保任意阶段可通过诊断包追溯（章程原则 VII）
- **FR-007**：端到端测试必须验证数据持久化的完整性，包括任务记录、执行历史、webhook 事件幂等去重（章程原则 II）
- **FR-008**：系统必须提供测试 fixtures，包括录播姬 webhook 事件样本与 AList 测试文件结构，纳入版本控制
- **FR-009**：端到端测试必须支持幂等重复运行，每次运行前清理上次状态（数据库、文件系统、临时文件）；测试中途失败时 MUST 保留失败现场（不立即清理），供维护者通过诊断系统（specs/009）定位问题，由下次运行前的强制清理保证幂等
- **FR-010**：系统必须通过二进制本地启动方式在项目目录准备 AList 与录播姬实例：下载对应平台可执行文件到项目指定目录，通过启动脚本运行，无需依赖 Docker 环境（Windows 开发环境优先，Linux 环境通过已有 specs/003-docker-deploy 方案覆盖）
- **FR-011**：端到端测试中录播姬事件必须通过 webhook payload 重放驱动产生：使用版本化的录播姬 webhook 事件样本（fixtures）直接向系统注入"录制完成"事件，驱动真实系统处理与真实 AList 同步链路；录播姬实例仅作为可选验证，不依赖真实直播源，以消除直播源不稳定对回归可重复性的阻塞（取代 2026-07-19 草案中"真实录制直播流"的方案）
- **FR-012**：端到端测试链路间必须串行执行（共享单一 AList/录播姬/系统实例与数据目录，禁止并行以避免端口与状态争抢），每条链路执行后独立清理状态以保证幂等性（对齐 FR-009）
- **FR-013**：端到端测试套件纳入 CI 但仅以定时任务方式运行（如 nightly），MUST NOT 在每次 PR/提交流水线中触发；CI 的 PR 流水线仅运行单元测试与集成测试层，E2E 因总时长约 60 分钟（SC-006）不适宜阻塞协作流水线
- **FR-014**：测试环境准备 MUST 采用动态端口分配策略：自动探测空闲端口并注入到 AList、录播姬与系统实例配置中，消除端口占用冲突风险，支撑 SC-005 新贡献者搭建成功率目标（禁止依赖固定端口假设）

### 关键实体 *（如果功能涉及数据则包含）*

- **测试环境**：由 AList 实例、录播姬实例与系统实例组成的端到端运行环境，三者真实交互
- **测试 fixtures**：录播姬 webhook 事件 payload 样本、AList 测试目录结构与媒体文件，作为测试输入的固定数据
- **测试 profile**：隔离端到端测试与常规测试的执行配置，控制外部依赖启动与清理
- **链路断言点**：端到端链路中可观察的验证点，包括 webhook 接收、任务创建、文件落盘、转码完成、日志 traceId 一致性

## 成功标准 *（强制）*

### 可衡量的结果

- **SC-001**：维护者可在 10 分钟内从干净项目目录完成端到端测试环境准备并首次运行通过
- **SC-002**：端到端测试覆盖至少 3 条核心业务链路（webhook 触发同步、手动同步任务、转码任务），每条链路可独立运行
- **SC-003**：测试金字塔补全后，单元测试覆盖率 > 80%、Repository 集成测试覆盖率 > 60%、外部 API 客户端集成测试覆盖全部公共方法、端到端测试覆盖全部核心链路
- **SC-004**：端到端测试在连续 3 次重复运行中全部真实执行且成功（基于 webhook payload 重放注入真实系统与真实 AList 链路，非 Mock；3 次必须全部真实通过），验证环境清理的幂等性与链路稳定性。因采用重放驱动，直播源不可用不再是 skip 候选场景
- **SC-005**：新贡献者按照文档独立完成端到端环境搭建的成功率 > 90%（通过贡献者反馈或文档走查验证）
- **SC-006**：端到端单链路全局执行超时阈值为 15 分钟，超时即标记失败并清理状态（防止转码异常或重放注入异常导致套件挂死），3 链路串行总套件上限约 60 分钟
